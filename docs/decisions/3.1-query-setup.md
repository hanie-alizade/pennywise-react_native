## Decisions

### D1 — `QueryClient` defaults and caching rationale
- **Context:** Pennywise is an online-first budgeting client where data changes primarily through deliberate user actions or monthly rollovers.
- **Options considered:**
  - A) *Zero stale time (`staleTime: 0`):* Refetches on every mount and navigation, resulting in UI flickering and wasted cell data.
  - B) *Extended stale time (5+ minutes):* Risk of viewing outdated budget lines after switching months or background edits.
  - C) *Balanced 30-second stale time (`staleTime: 30 * 1000`) with disabled window focus refetching:* Retains instant navigation between tabs without unnecessary refetch churn.
- **Chosen:** Option C.
- **Why:** Mandated by `docs/ARCHITECTURE.md` section "Server state". 30 seconds allows rapid switching between Overview, Categories, and Settings tabs without constant network spinners.
- **Trade-offs accepted:** Changes made on external web/backend interfaces during an active 30-second window require pull-to-refresh to appear.
- **Revisit when:** Real-time push notifications or WebSockets are introduced post-MVP.

### D2 — Query retry policy
- **Context:** Request failures must be handled gracefully without bombarding servers with doomed requests.
- **Options considered:**
  - A) *Default retry (3 times for all errors):* Repeatedly retries 401 Unauthorized, 404 Not Found, or 422 Unprocessable errors, slowing UI feedback and wasting battery.
  - B) *No retry on 4xx; limited retry (max 2) on network errors:* Inspects `ApiError.status` and `isNetworkError()`.
- **Chosen:** Option B.
- **Why:** Client errors (4xx) cannot succeed without client-side correction (e.g. login or input fix). Transient radio/packet drops (`NETWORK_ERROR`) benefit from a small number of retries before alerting the user.
- **Trade-offs accepted:** 5xx server bugs will not retry automatically.
- **Revisit when:** Exponential backoff policies need tuning in Phase 6.

### D3 — `StateBlock` component API
- **Context:** Every screen that fetches remote data must show consistent loading indicators, user-friendly error banners with retry triggers, and clean empty states.
- **Options considered:**
  - A) *Ad-hoc loading and error views per screen:* Leads to fragmented layout styles and duplicate retry handlers.
  - B) *Unified `StateBlock` component with `type: "loading" | "error" | "empty"`:* Encapsulates activity spinners, accessible alert roles (`accessibilityRole="alert"`), and secondary action buttons using theme tokens.
- **Chosen:** Option B.
- **Why:** Provides a single, predictable layout pattern for asynchronous state management.
- **Trade-offs accepted:** Complex custom empty illustrations need optional slot extensions.
- **Revisit when:** Animated SVG illustrations are added to empty states.

### D4 — Source of pull-to-refresh state
- **Context:** When the user pulls down the Categories list, the refresh spinner should remain visible only while the network request is in flight.
- **Options considered:**
  - A) *Local `useState(false)` with manual toggling:* Fragile; prone to getting stuck in spinning state if promises reject unexpectedly.
  - B) *TanStack Query `isRefetching` directly bound to `RefreshControl.refreshing`:* Derived state; automatically synchronizes with query fetch lifecycle.
- **Chosen:** Option B (`isRefetching`).
- **Why:** Eliminates state desynchronization bugs. Initial loads show a centered `StateBlock` spinner (`isLoading && !isRefetching`), while subsequent pull actions show the native top pull indicator without unmounting the list.
- **Trade-offs accepted:** Multiple simultaneous query refetches require composing refetch states.
- **Revisit when:** Multi-query composite dashboard screens in Phase 4.

## Gotchas and edge cases handled

- Differentiated initial screen loading (`isLoading && !isRefetching`) from background pull-to-refresh (`isRefetching`), ensuring existing category items remain visible during swipe refreshes.
- Configured `.env` to point `EXPO_PUBLIC_API_URL` to `http://localhost:3000` (the Prism mock server).
