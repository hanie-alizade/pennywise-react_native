## Decisions

### D1 — Native `fetch` vs Axios / Ky
- **Context:** Pennywise needs a reliable HTTP client for cross-platform iOS and Android requests.
- **Options considered:**
  - A) *Axios / Ky:* Feature-rich with interceptors, but introduces additional external dependencies, bundle weight, and potential React Native networking incompatibilities.
  - B) *Native `fetch` with custom `request<T>()` wrapper:* Built directly into modern JavaScript runtimes, Hermes, and React Native.
- **Chosen:** Option B (`fetch`).
- **Why:** Zero extra dependencies, fully standards-compliant, and allows precise control over header formatting, timeout abort signals, and error envelope parsing.
- **Trade-offs accepted:** Interceptors and token refresh must be explicitly coordinated in client code rather than middleware chains.
- **Revisit when:** File upload streaming or background upload tasks require specialized libraries.

### D2 — Timeout mechanism and duration
- **Context:** Mobile connections can hang indefinitely on spotty cell towers without throwing an immediate error.
- **Options considered:**
  - A) *`Promise.race` with delay timers:* Leaves the underlying native request alive in the background after timing out.
  - B) *`AbortController` with a 15-second timeout:* Calls `controller.abort()`, terminating native sockets and freeing connection pool slots.
- **Chosen:** Option B with 15000ms (15 s) default timeout.
- **Why:** Standard Web API supported natively in React Native. Cancels underlying socket activity immediately and maps the abort event to `ApiError` with code `NETWORK_ERROR`.
- **Trade-offs accepted:** Slow analytical endpoints or heavy batch operations would need a custom `timeoutMs` override.
- **Revisit when:** Specific endpoints require longer timeouts (e.g. export/import).

### D3 — Error normalization shape (`ApiError`)
- **Context:** UI layers must consistently distinguish between network outages, HTTP validation errors, and unexpected server failures.
- **Options considered:**
  - A) *Throwing raw `Response` or generic `Error`:* Leaks HTTP implementation details into components and hooks.
  - B) *`ApiError` class extending `Error` with `status`, `code`, `message`, and `details`:* Non-2xx responses are parsed against `errorSchema`. If parsing succeeds, backend error codes and field validation paths are preserved. Unreachable servers or aborts produce `status: 0` and `code: "NETWORK_ERROR"`.
- **Chosen:** Option B.
- **Why:** Provides a single, uniform error interface across the entire app. The helper `isNetworkError(err)` immediately tells UI components to render offline banners.
- **Trade-offs accepted:** Non-standard server errors without JSON envelopes fall back to status text.
- **Revisit when:** GraphQL or gRPC error protocols are introduced.

### D4 — Avoiding circular imports via `configureAuth`
- **Context:** `request()` needs access to the current access token and refresh logic, but importing `AuthProvider` directly inside `api/client.ts` causes an import cycle (`providers -> api -> providers`).
- **Options considered:**
  - A) *Global mutable token variable exported from `tokenStorage`:* Tight couples the HTTP client directly to persistent storage.
  - B) *Dependency injection callback pattern (`configureAuth`):* `client.ts` exports `configureAuth({ getAccessToken, refresh, onSignedOut })`. `AuthProvider` initializes this hook on mount.
- **Chosen:** Option B.
- **Why:** Completely decouples `src/api` from React state and providers. Satisfies strict downward import architecture (`constants -> schemas -> types -> helpers -> api -> apiHooks -> providers -> components -> app`).
- **Trade-offs accepted:** Requests made before `configureAuth` executes will not attach authorization headers.
- **Revisit when:** Multi-account switching requires request-scoped client instances.

### D5 — Response validation strategy (runtime vs compile-time)
- **Context:** Decide whether every 2xx response should be parsed at runtime with Zod or trusted via generated TypeScript types.
- **Options considered:**
  - A) *Zod parse every 2xx response:* Guaranteed runtime schema safety, but high CPU/memory overhead on mobile devices and requires maintaining double schemas (OpenAPI + Zod).
  - B) *Parse boundary errors with Zod; trust 2xx response types from generated OpenAPI definitions:* Strict Zod validation on error envelopes and environment variables; 2xx JSON is typed via TypeScript generics from `openapi-typescript`.
- **Chosen:** Option B.
- **Why:** Maximum mobile performance and developer ergonomics without redundant schema maintenance. The backend contract in `docs/openapi.yaml` is the single authoritative contract.
- **Trade-offs accepted:** If the backend emits undeclared fields or mismatched 2xx shapes, errors will surface during UI rendering rather than in the client request parser.
- **Revisit when:** Untrusted third-party APIs are integrated.

## Gotchas and edge cases handled

- Handled HTTP 204 (No Content) responses cleanly without calling `response.json()`, avoiding unexpected JSON parse exceptions on DELETE requests.
- Mapped both `controller.signal.aborted` timeouts and `TypeError: Network request failed` into normalized `ApiError` instances with `ERROR_CODES.NETWORK_ERROR`.
