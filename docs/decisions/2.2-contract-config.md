## Decisions

### D1 — OpenAPI Codegen vs hand-written types
- **Context:** The Pennywise mobile client is an API-first client whose source of truth is `docs/openapi.yaml`. Keeping hand-written types in sync with backend contract changes is prone to drift.
- **Options considered:**
  - A) *Hand-written TypeScript interfaces:* High maintenance overhead; contract discrepancies are only detected at runtime.
  - B) *`openapi-typescript` code generation with readable aliases:* Generates exact types from OpenAPI 3.0 schema directly into `api.generated.ts`. `src/types/index.ts` re-exports clean domain aliases.
- **Chosen:** Option B (`openapi-typescript`).
- **Why:** Code generation guarantees 100% type fidelity with the backend specification with zero manual translation errors. Re-exporting aliases maintains clean, readable imports across the codebase (`import type { MonthView } from "@/types"`).
- **Trade-offs accepted:** Generated types file (`api.generated.ts`) is large and should never be manually edited.
- **Revisit when:** Backend moves away from OpenAPI to GraphQL or tRPC.

### D2 — Mock server scope and limits
- **Context:** Mobile UI development requires testing states before the private backend repository is fully deployed or when offline.
- **Options considered:**
  - A) *Custom MSW (Mock Service Worker) handlers:* Requires writing and maintaining duplicate mock logic in client code.
  - B) *Prism CLI (`@stoplight/prism-cli`):* Serves dynamic mock responses generated directly from `docs/openapi.yaml` examples and schemas without writing mock code.
- **Chosen:** Option B (`npm run mock`).
- **Why:** Zero maintenance overhead; immediately reflects any updates made to `docs/openapi.yaml`.
- **Trade-offs accepted:** Prism only returns canned responses based on schema examples; it does not persist writes, validate complex relational rules, or run real auth session lifecycles.
- **Revisit when:** Automated end-to-end integration tests need stateful multi-step persistence.

### D3 — Environment validation behavior on failure
- **Context:** Misconfigured API URLs (e.g. invalid scheme, missing host) lead to silent, hard-to-debug runtime network errors.
- **Options considered:**
  - A) *Silent fallback to `http://localhost:3000`:* Hides environment configuration bugs in production or staging builds.
  - B) *Strict Zod parsing throwing an immediate `Error`:* Validates `process.env.EXPO_PUBLIC_API_URL` during startup; throws a clear formatted error if invalid.
- **Chosen:** Option B.
- **Why:** Fails fast with descriptive error messages before any API requests execute, preventing undefined behavior.
- **Trade-offs accepted:** A misconfigured environment crashes at startup rather than attempting a best-effort fallback.
- **Revisit when:** Multi-environment dynamic runtime switching is implemented.

### D4 — `as const` objects vs TypeScript enums
- **Context:** Need fixed domain values for error codes, category types, and storage keys.
- **Options considered:**
  - A) *TypeScript `enum`:* Produces idiosyncratic JavaScript lookup objects at runtime, conflicts with some bundlers/transpilers, and has well-documented type safety quirks.
  - B) *`as const` objects with derived union types:* Pure JavaScript objects (`export const CATEGORY_TYPE = { ... } as const; export type CategoryType = ...`).
- **Chosen:** Option B.
- **Why:** Mandated by `docs/CONVENTIONS.md` section 3 and TypeScript best practices. Eliminates runtime surprises and works seamlessly with standard string literals.
- **Trade-offs accepted:** Slightly more verbose type derivation syntax.
- **Revisit when:** Never; `as const` is standard in modern TypeScript.
