## Decisions

### D1 — `TextField` controlled-API shape
- **Context:** Form inputs across auth, month creation, and transaction screens require strict controlled state, clear validation feedback, and full accessibility support.
- **Options considered:**
  - A) *Uncontrolled `TextInput` with refs:* Fast for raw DOM, but incompatible with React Hook Form's controlled state model and declarative validation feedback in React Native.
  - B) *Controlled component exposing `value`, `onChangeText`, `label`, `error`, and `helperText`:* Fully controlled and easily bound directly or via `Controller`.
- **Chosen:** Option B.
- **Why:** Complies with `docs/CONVENTIONS.md` section 5 ("React Hook Form + Controller for every TextInput"). Focus state (`isFocused`) is managed internally to highlight the border with `colors.primary`, while error state (`hasError`) automatically overrides with `colors.error`.
- **Trade-offs accepted:** Each keystroke triggers a component re-render; acceptable given isolated leaf input scope.
- **Revisit when:** High-frequency numeric formatting inputs in Phase 4 require debounced or masked input wrappers.

### D2 — Encapsulation of error styling
- **Context:** Input validation errors must be immediately obvious and accessible without requiring consumers to write repetitive border or color styling.
- **Options considered:**
  - A) *External styling:* Consumers pass red borders and render separate error text below each input.
  - B) *Self-contained error handling:* `TextField` receives an optional `error` string; when present, it renders `colors.error` border styling and an accessible `AppText` error message below the field.
- **Chosen:** Option B.
- **Why:** Centralizes visual styling and accessibility attributes (`accessibilityHint` set to the error message), preventing inconsistent error presentation across screens.
- **Trade-offs accepted:** Custom multi-error layouts require extending `TextField` props.
- **Revisit when:** Complex server error matrices with multiple field-level tags need specialized error rendering.

### D3 — `FlatList` configuration and virtualization choices
- **Context:** Pennywise overview and transactions screens display numerous budget lines and transaction rows. Scrolling must remain 60fps on low-end devices without memory bloat.
- **Options considered:**
  - A) *`ScrollView` mapping rows:* Simple, but instantiates all rows simultaneously, causing high memory usage and frame drops on large lists.
  - B) *`FlatList` with default settings (`windowSize=21`):* Keeps 10 screens worth of rows above and below mounted, causing excess memory footprint.
  - C) *`FlatList` tuned with `windowSize=5`, `initialNumToRender=15`, and `maxToRenderPerBatch=10`:* Retains minimal unrendered buffers while eliminating scroll stutter.
- **Chosen:** Option C.
- **Why:** Conserves memory and native view count on budget Android devices. The form header is embedded inside `ListHeaderComponent` instead of nesting a `FlatList` in a `ScrollView` (which triggers React Native nesting warnings and breaks windowing).
- **Trade-offs accepted:** Fast flings may briefly expose blank space while batch renders complete.
- **Revisit when:** Complex section headers in Phase 4 require migration to `SectionList`.

## Gotchas and edge cases handled

- **Nested scroll avoidance:** Mounted `FlatList` directly inside `<Screen scrollable={false}>` and placed the input demonstration inside `ListHeaderComponent` to prevent vertical scroll nesting warnings and preserve smooth virtualization.
- **Keyboard avoidance:** Ensured `keyboardShouldPersistTaps="handled"` on the `FlatList` so tapping submit or other fields dismisses/switches focus without phantom taps.
- **No magic numbers:** Used `typography.fontSize.xs` and `typography.fontSize.sm` for `Badge` sizing, and `spacing` tokens for separators and card paddings.
