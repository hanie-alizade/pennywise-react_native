## Goal

Establish the application's central design token system and implement core presentational UI components (`AppText`, `Screen`, `Button`) with zero hardcoded magic numbers or hex codes outside the theme tokens.

## Decisions

### D1 — Design token architecture and structure
- **Context:** Pennywise requires a calm, restrained teal/mint visual identity without hardcoded magic numbers or hex codes in components. All colors must be centralized in `src/theme/colors.ts` to satisfy repo rules.
- **Options considered:**
  - A) *Monolithic single theme file:* Simple, but grows rapidly and makes imports harder to reason about.
  - B) *Modular token files with a single barrel export:* Independent files for `colors`, `spacing`, `radius`, `typography`, and `shadows`, assembled in `src/theme/index.ts`.
- **Chosen:** Option B.
- **Why:** Keeps each token category concise (< 80 lines) while presenting a single `@/theme` import surface. All hex codes reside strictly in `colors.ts`, enabling `shadows.ts` and `typography.ts` to cleanly reference `colors`.
- **Trade-offs accepted:** Requires exporting both flat namespaces (`colors`, `spacing`) and the composite `theme` object.
- **Revisit when:** Dynamic dark mode or multi-theme switching is introduced post-MVP.

### D2 — Using `Pressable` for interactive elements
- **Context:** Need consistent touchable behavior with minimum 44x44 touch targets and state handling (hover/pressed/disabled/loading).
- **Options considered:**
  - A) *`TouchableOpacity` / `TouchableHighlight`:* Legacy React Native APIs with baked-in opacity or underlay behaviors that are difficult to customize per state.
  - B) *`Pressable`:* Modern React Native core API with functional `style` callback based on `{ pressed }` interaction state.
- **Chosen:** `Pressable`.
- **Why:** Recommended by React Native core and project conventions (`CONVENTIONS.md` section 5). Allows clean styling transitions between normal and pressed states (e.g. `primaryHover`, `accentSoft`) without manipulating opacity alone.
- **Trade-offs accepted:** Pressed state styling is manually specified per variant rather than automatic.
- **Revisit when:** Gesture-driven animations require `react-native-gesture-handler`.

### D3 — `Screen` safe area and keyboard handling per platform
- **Context:** Screens must handle notch/dynamic island insets and prevent virtual keyboards from covering content without double-insetting on Android.
- **Options considered:**
  - A) *`SafeAreaView` from React Native core:* Deprecated / inconsistent across modern iOS devices with dynamic islands.
  - B) *`react-native-safe-area-context` hooks + `KeyboardAvoidingView` with platform branching:* Insets derived from `useSafeAreaInsets()`; `KeyboardAvoidingView` behavior set to `"padding"` on iOS and `undefined` on Android.
- **Chosen:** Option B.
- **Why:** Android handles window resizing natively via `adjustResize` in `app.json`, so adding `"padding"` or `"height"` on Android causes erratic jumpiness. iOS requires `"padding"`.
- **Trade-offs accepted:** Scrollable screens need `keyboardShouldPersistTaps="handled"` on the inner `ScrollView`.
- **Revisit when:** A screen requires custom edge-to-edge transparent headers.

### D4 — Variant APIs of `AppText` and `Button`
- **Context:** Ensure readable typography hierarchy and predictable button styling across all screens.
- **Options considered:**
  - A) *Granular styling props (e.g. `size="lg" weight="bold" color="primary"` on text):* Leaks style decisions into screen code.
  - B) *Coarse semantic variants (`title`, `body`, `label`, `mono` for `AppText`; `primary`, `secondary`, `danger`, `ghost` for `Button`):* Keeps components consistent with minimal boilerplate.
- **Chosen:** Option B.
- **Why:** Strongly constrains UI variations to the design kit while allowing local `style` overrides when strictly necessary.
- **Trade-offs accepted:** Rare one-off typography treatments require composing base variants with custom StyleSheet overrides.
- **Revisit when:** Design system expands with sub-variants in Phase 4/5.

## Gotchas and edge cases handled

- Defined `touchTargets.min = 44` in `spacing.ts` so minimum touch dimensions for accessibility are first-class tokens rather than magic numbers.
- Integrated `ActivityIndicator` directly within `Button` with accessible busy state (`accessibilityState={{ busy: true }}`) and matching variant contrast colors.
- Implemented `allowFontScaling={true}` by default on `AppText` so user system font accessibility preferences are preserved.
