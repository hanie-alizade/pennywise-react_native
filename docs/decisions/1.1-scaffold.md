## Decisions

### D1 — Expo SDK and template choice
- **Context:** Pennywise is a mobile budgeting client requiring fast iteration on iOS and Android with strict typing and file-based routing.
- **Options considered:**
  - A) *Expo SDK 57 with blank TypeScript template and Expo Router:* Modern React 19 / React Native 0.86 support, first-class file-based routing, active maintenance, seamless Expo Go compatibility.
  - B) *Bare React Native CLI:* Requires manual native project maintenance and linking without built-in web or Expo Go support; excessive overhead for an API-driven app.
- **Chosen:** Expo SDK 57 with Expo Router and TypeScript.
- **Why:** Delivers rapid cross-platform execution, standard tooling, and managed native modules without premature native configuration drift.
- **Trade-offs accepted:** Dependency updates are tied to Expo release cycles; native library additions must be compatible with Expo Go or require Development Builds later.
- **Revisit when:** Custom native modules with non-Expo native code are required.

### D2 — Alias setup (`@/` to `src`)
- **Context:** Deep relative imports (e.g. `../../components/...`) are error-prone and prohibited by repo conventions.
- **Options considered:**
  - A) *TypeScript `paths` only:* TypeScript understands `@/*`, but Metro may fail at bundle time without custom babel/metro configuration if not supported.
  - B) *TypeScript `paths` combined with Expo's built-in Metro resolver:* Expo Metro config natively honors `tsconfig.json` paths out of the box.
- **Chosen:** Option B (`tsconfig.json` `"paths"` combined with `metro.config.js` invoking `@expo/metro-config`).
- **Why:** Standard, officially supported approach in modern Expo without third-party babel plugins like `babel-plugin-module-resolver`.
- **Trade-offs accepted:** Imports must strictly follow `@/<subfolder>` barrels as mandated in repo conventions.
- **Revisit when:** Metro path resolution fails on unexpected platforms or monorepo restructuring.

### D3 — Custom lint rules in ESLint
- **Context:** Enforce codebase consistency, no default exports in `src/`, explicit type imports, and forbid debugging leftovers like `console.log`.
- **Options considered:**
  - A) *Standard `eslint-config-expo` alone:* Misses import style enforcement and allows `console.log` and default exports.
  - B) *Flat ESLint config adding `no-console`, `eqeqeq`, `@typescript-eslint/consistent-type-imports`, and `no-restricted-exports`:* Catches conventions at lint time.
- **Chosen:** Option B.
- **Why:** Mechanically prevents bad patterns before review or commit.
- **Trade-offs accepted:** ESLint flat config setup requires extracting `@typescript-eslint` plugin reference from `eslint-config-expo`.
- **Revisit when:** `eslint-config-expo` ships updated flat config presets natively exposing these options.

### D4 — Scope and limits of `scripts/check-rules.mjs`
- **Context:** Certain repository hard rules (no hex colors outside `src/theme`, no `@ts-ignore`, no `parseFloat` for currency calculations, no deep relative imports) cannot be conveniently or reliably expressed in standard ESLint rules without custom plugins.
- **Options considered:**
  - A) *Custom ESLint plugin package:* High maintenance burden and extra local dependency packaging.
  - B) *Lightweight standalone Node.js check script (`scripts/check-rules.mjs`):* Zero external dependencies, fast execution, simple regex/line-based AST checks.
- **Chosen:** Option B.
- **Why:** Self-contained, easily audited, fast, and exits non-zero on rule violations.
- **Trade-offs accepted:** Line/regex matching has limits (e.g. cannot parse complex multiline syntax trees; uses heuristic keywords like `amount`/`money`/`price` for `parseFloat`).
- **Revisit when:** False positives or negatives occur during complex refactoring.

### D5 — Package manager choice
- **Context:** Consistency across developer environments and deterministic installs.
- **Options considered:**
  - A) *npm (`package-lock.json`):* Standard default bundled with Node.js; supported everywhere without extra installation.
  - B) *pnpm / yarn:* Faster in some environments, but adds tooling prerequisites.
- **Chosen:** npm (`npm`).
- **Why:** Aligns with standard Expo CLI recommendations and project conventions without requiring custom corepack activation.
- **Trade-offs accepted:** Install times can be marginally slower than pnpm.
- **Revisit when:** Monorepo architecture is adopted.
